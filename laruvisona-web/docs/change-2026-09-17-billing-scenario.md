# 2026-09-17 申し込み〜決済〜解約を、人の手なしで通せるようにした

## なぜ

決済まわりは「**課金は通ったのに何かが用意されていない**」という形で壊れる。
画面には何も出ないので、実際に通してみるまで誰も気づけない。

これまで確かめる方法は、実カードで最後まで申し込むことだけだった。
最後のボタンは人が押す必要があり、押すたびに本物の請求が立つので、何度も回せない。
結果として、**一度も通しで確かめられていない**状態が続いていた。

## やったこと

`npm run test:billing` で、申し込み〜決済〜解約が最後まで走る。外部へは一切出ない。
実際の請求は立たない。人の手も要らない。

```
bash tests/billing/run.sh
  ok   偽の署名では受け付けない
  ok   契約が通ると、プランと契約期間が入る
  ok   契約が通ると、開始メールが正しい宛先へ1通
  ok   LARUbotが付くプランなら、登録が飛ぶ
  ok   同じ通知が二度届いても、メールが二重にならない
  ok   LARUbotが無いプランでは、登録を飛ばす
  ok   運営の契約は、課金の対象にしない
  ok   支払いが落ちると past_due になり、本人へ知らせる
  ok   支払いが通ると active に戻り、契約終わりが伸びる
  ok   プランを上げると、プランが入れ替わって知らせが飛ぶ
  ok   解約すると、プランも契約IDも消えて知らせが飛ぶ
  ok   知らないユーザーの通知で、他人の行を書き換えない
  通過 12 / 失敗 0
```

### 仕組み

Stripe・Supabase・メール（Resend）・LARUbot を替え玉に差し替え、
**こちらのコードだけ本物のまま**動かす。

| 差し替える先 | 切り替え方 |
|---|---|
| Supabase（PostgREST・GoTrue） | `NEXT_PUBLIC_SUPABASE_URL`（ビルド時に埋め込まれるので番号は 54999 固定） |
| Stripe | `STRIPE_API_BASE`（`lib/stripe.ts` の安全弁つき・後述） |
| メール | `RESEND_BASE_URL`（resend パッケージが読む） |
| LARUbot | `LARUBOT_API_URL`（`lib/larubot-provision.ts` が読む） |

**替え玉でないもの**（＝本物を通っている）:

- webhookの署名検証（本物の `stripe.webhooks.constructEvent`）
- プラン付与、契約期間の計算、メール本文の中身、LARUbot登録の中身、冪等性の鍵

### Stripeの宛先を差し替える安全弁

`lib/stripe.ts` に `STRIPE_API_BASE` を足した。ここが緩むと**本番の鍵のまま請求が別の宛先へ飛ぶ**ので、
次の両方を満たしたときだけ効かせる。

1. 鍵が `sk_live…` でないこと
2. 宛先がループバック（`127.0.0.1` / `localhost` / `::1`）であること

どちらか一方でも欠けたら何もせず本物の `api.stripe.com` へ行く。
`tests/stripe-endpoint.test.ts` で、本番鍵・外部ホスト・壊れたURLのすべてが弾かれることを固定した。
検証の道具に本物の鍵が書かれていないことも、同じテストで見ている。

## テストが本当に効くか確かめた

緑になるテストは、**壊したときに赤くなって初めて意味がある**。
コードをわざと3か所壊して、全部が赤くなることを確かめた。

| 壊し方 | 結果 |
|---|---|
| 契約開始日を `start_date` → `current_period_start` に | 「contract_starts_at が current_period_start を見ている」で赤 |
| メールの冪等キーを `event.id` → `Date.now()` に | 「同じイベントなのに鍵が違う」で赤（再送で2通届く） |
| LARUbot登録の屋号を空文字に | 「'' !== 'テスト工務店'」で赤 |

3つとも狙いどおりの文言で落ちたので、元に戻した。

このうち1つ目は、**替え玉の `start_date` と `current_period_start` を同じ値にしていたら
検出できなかった**。作った直後は同じ値で、テストは通るのに何も証明していなかったので、
わざと1ヶ月ずらしてある。

## 確かめないと決めたこと

- **Stripeのカード入力画面そのもの。** 向こう側の画面で、こちらの資産ではない。
  自動で埋めるべきものでもない。
- **Stripeが実際にその価格で請求するか。**
  こちらは `npm run check:production` の price-check が、本番の価格IDを読んで確かめている。

つまり残るのは「Stripeの画面で実カードを通したときに、本当に決済が成立するか」だけ。
そこから先（プラン付与・メール・LARUbot・解約）は、これで毎回自動で確かめられる。

## 走らせ方

```
npm run build
npm run test:billing
```

`tests/http/run.sh` と同じ 54999番を使うので、**同時には走らせられない**。
片方が立っていると、その旨を出して止まる。

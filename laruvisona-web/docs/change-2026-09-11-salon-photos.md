## 2. 写真の入れ方

### 配信用の作り方（`scripts/salon-photos.mjs`）

原画はPNGで1枚4〜7MB。**そのまま配らない。**
この作品のギャラリーとスタッフの節は、公開HTMLでは素の `<img src>` で出る
（`srcset` を持たない）。**既存の配信方式に合わせ**、JPEG 1枚ずつに書き出した。

| スタッフ3枚 | 2048×2048 PNG | **512×512 JPEG** | 直径148pxの円 |

| ファイル | 書き出した直後 | **リポジトリに入っているもの** |
|---|---|---|
| style-1.jpg | 72,911 | **78,682** |
| style-2.jpg | 82,012 | **87,783** |
| style-3.jpg | 69,018 | **74,789** |
| style-4.jpg | 103,884 | **109,655** |

| **合計** | **391,033 B（381.9 KiB）** | **431,430 B（421.3 KiB）** |

**単位**: この文書の「KB」はすべて **KiB（1024バイト）**。
以前ここに書いた「382KB」は、書き出した直後の 381.9 KiB のこと。

**差は1枚あたりちょうど +5,771 バイト**で、7枚で +40,397 バイト。

**ファイルを手元へ書き戻す経路で付いたもの**。

圧縮条件は同じで、再圧縮はしていない。**本番で配られるのはリポジトリ側＝431,430 B**。
（この区画を落とせば40KB弱減るが、生成画像の来歴を残す情報でもあるため、
今回は触っていない。落とすかどうかは別に決める）

### staff-1 の白い四隅

原画に円形の背景と白い四隅が焼き込まれている（生成時点のもの。納品側も記録済み）。

用途は指示どおり**中央の円形表示に限定**。矩形での利用や拡大表示には使っていない。

## 3. 直した不具合：下の写真が優先で読み込まれていた

`lib/html-export.ts` は、`loading` の指定が無い `<img>` のうち**1枚目**に
`fetchpriority="high"` を付けていた。「1枚目＝最初の画面の写真」という前提。

ところが最初の画面が写真つき（`<picture>`）の作品では、その `<img>` は自分で
`loading="eager" fetchpriority="high"` を書いている。すると**その次に見つかる
「loading 未指定の1枚目」＝ページのずっと下にあるスタッフ写真**に、
優先の指定が付いていた。

```
（直す前）<img fetchpriority="high" decoding="async" src="/salon/staff-1.jpg" …
（直した後）<img loading="lazy" decoding="async" src="/salon/staff-1.jpg" …
```

最初の画面の写真が自分で優先を宣言している場合は、ほかの画像を優先しないようにした。
単体を1件足してある（`tests/published-html.test.ts`）。

これは**この作品だけの話ではない**。最初の画面に写真を置いた顧客サイトすべてで
起きていた。`EXPORT_VERSION` を 11 に上げたので、出荷時の作り直しで直る。

### 直しの直しː 判定がページをまたいでいた（Codex 指摘）

上の直し方には穴があった。**全ページを繋いだHTML**に対して
「自分で優先を書いている画像があるか」を見ていたので、
複数ページの作品では次のようになる。

```
1ページ目: 先頭が team ブロック（/first-visible.jpg）
2ページ目: 写真つきヒーロー（/other-hero.jpg）。hidden で出る
→ 2ページ目のヒーローを見て「優先済み」と判断し、
   表示中の /first-visible.jpg まで loading="lazy" になっていた
```

判定を**ページごとに閉じ**、優先を与えるのは**最初のページだけ**にした
（2ページ目以降は `hidden` で始まるので、そこへ優先を配らない）。
Codex の再現条件をそのまま回帰に足してある（`tests/published-html.test.ts`）。

なお、**写真つきヒーロー自身が書く `loading="eager" fetchpriority="high"` は
そのまま**にしてある。隠れているページのヒーローも、これまでどおり自分で優先を
宣言する。ここを変えると単一ページの作品にも影響が出るので、今回は触っていない
（隠れているページの先読みをどうするかは、別に決める）。

## 5. 転送量と速さ（写真を入れる前と後）

同じ公開HTMLのまま、**画像の置き場所だけ**を差し替えて比べた
（`serve-published.mjs`。顧客ページが返すのはこのHTMLそのもの）。
条件は 1.6Mbps・150ms・CPU 1/4・**顧客の選択書体（明朝）を実際に読み込む**・3回の中央値。

### 下の写真の転送量

| | 写真なし（プレースホルダ） | **写真あり** |
|---|---|---|
| スタイル4枚＋スタッフ3枚（書き出した直後の比較） | 180 KiB | **381.9 KiB** |

**+202 KiB。** リポジトリ側では 421.3 KiB（上の表）。

#### 「あとで読む」指定と、実際に取りに行った時刻は別

HTMLの**指定**は、7枚すべて `loading="lazy"`、`fetchpriority` は無し
（`photo-check.mjs` が毎回見ている）。

ただし**指定＝取りに行かない、ではない**。ブラウザは画面の少し先にある画像を
先読みする。スクロールしないまま4秒待って、実際に何枚落としたかを測った:

| 条件 | PC 1440×900 | スマホ 390×844 |
|---|---|---|
| 1.6Mbps・150ms・CPU 1/4 | **0枚** | **0枚** |
| 回線・CPUの制限なし（手元） | 7枚・381.9 KiB（load完了476ms に対し 321〜326ms） | 3枚・62 KiB（441ms） |

どちらの条件でも、**最初に取りに行くのは最初の画面の写真**で、
下の写真に優先の指定は付かない。
「最初の表示には乗らない」とは言えない。言えるのは
**「優先されない」「回線が細いほど後回しになる」**まで。

### 初回表示

| | 写真なし | **写真あり** | 目安 |
|---|---|---|---|
| LCP（PC） | 0.94秒 | **0.96秒** | 2.5秒 |
| LCP（スマホ） | 0.98秒 | **0.91秒** | 2.5秒 |
| CLS（PC / スマホ） | 0.0006 / 0.0231 | **0.0006 / 0.0199** | 0.1 |

差は測り直しのばらつきの範囲。LCPの対象はどちらも最初の画面の写真で、
下の写真を入れても変わっていない。

> ページ全体の転送は約4.4MBだが、その大半は**手元に置いた明朝の実ファイル**
> （1書体1.4MB×3）。本番の Google Fonts は使う文字の範囲ごとに分けて配るので、
> 実際の訪問者がこの量を落とすわけではない。ここでの比較に使うのは写真の差分だけ。

## 6. 測り方について（正直に）

この作業環境では、**本番ビルドのサーバから手元のSupabase代替へ接続できなかった**
（`fetch failed`）。原因は環境側で、コードの変更ではない。そのため:

- 保存→公開→表示・利用者の保存・一括再生成の検査は、**開発サーバ**で実行した
- 写真の検査（23件）も開発サーバ
- **速さと転送量は**、保存済みの公開HTMLをそのまま静的に配って測った
  （アプリを挟まない。顧客ページが返すのはこのHTMLそのもの）

公開HTMLの中身はどちらでも同じだが、**本番ビルドのアプリ経由で測った数字ではない**。
前回までの数字（結い庵 PC 1.75秒など）とは測り方が違うので、直接は比べられない。

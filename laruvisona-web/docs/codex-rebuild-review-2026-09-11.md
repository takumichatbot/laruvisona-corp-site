## 公開前の修正

### R1 / P1: script内のJSONから抜け出せる

`lib/html-export.ts:744`、`app/laruHP/studio/page.tsx:156`。

`JSON.stringify(rawValue('targetDate'))` はHTMLの `</script>` を無害化しない。countdownのtargetDateに `</script><script>parent.__laruReviewProbe=1</script>` を渡してexportし、Studioと同様にsandboxなしのsrcdoc iframeへ入れると、Chromeで親windowの値が1になった。

本文のエスケープやdangerouslySetInnerHTMLの撤去だけでは防げていない。HTML内script用のJSON直列化を共通化し、少なくとも `<` をUnicodeエスケープして、JSON-LDを含む全ての埋め込みへ適用する。URL・CSS・HTML・JavaScript文字列の処理を混同しない。customCssのstyle終了タグなどの経路も点検する。プレビューは親の認証済み画面から分離し、必要な選択通知は送信元確認付き通信で実装する。親DOMに届かないことを実ブラウザで固定する。

### R2 / P1: 保存中・保存失敗でも公開ボタンが有効

`app/laruHP/studio/page.tsx:980`。公開ボタンが除外する保存状態はdirtyだけで、savingとfailedを除外していない。公開処理自体（493行付近）も保存状態を確認せず、保存済みDBデータの公開APIを呼ぶ。このため画面の最新内容と違うものを「この内容で公開し直す」ことになる。

公開可能なのは現在の編集が確実に保存された状態だけにする。保存中の追加編集、保存失敗後の公開、二重クリックを含めて検証する。reloadもdirtyしか確認していないので、failed時の入力破棄を防ぐ。

### R3 / P1: 旧サイトを開くとdesignが暗黙に追加される

`app/laruHP/studio/page.tsx:381`。designがない旧サイトにDEFAULT_DESIGNを入れ、toExportSettingsがプレビューと保存の両方へ渡す。実exportで従来はなかった `--lhp-d-ink` 等の全体CSSが追加されることを確認した。色、余白、角丸、写真比率等を指定するため、既存の見え方を保つ既定値とは言えない。

未設定を未設定のまま保持し、利用者が新しいデザイン設定を採用した時だけ追加する。旧サイトを開く→文章だけ変更→保存→再公開でdesignが増えず、見た目を変えない試験を入れる。

### R4 / P1: デモの画像を通常の配信経路に含めていない

`components/lp/AssembleDemo.tsx:31` 以降。`/salon/hero-*.jpg/avif/webp` を使用しているが、現checkoutにpublic/salonはなく、Git管理された配信ファイルもない。通常のpackage.jsonのbuildはnext buildのみ。READMEの手動コピーは隔離検証の手順であり、通常デプロイへの同梱保証ではない。

必要ファイルを正式なpublic資産に含めるか、通常ビルドに再現可能な準備処理を組み込む。クリーンなcheckoutから標準手順だけで起動し、src/srcsetで実際に選ばれる画像をHTTPで検証する。

### R5 / P1: 自社ページだけの公開と、全顧客の自動再生成が分離されていない

`docs/rebuild-migration-2026-09-11.md:38`、`server.js:202` 以降、`lib/html-export.ts:8`。

手順は自社2ページだけ先行公開としている一方、現コードはADMIN_SECRET設定時に起動60秒後、旧版の全公開サイトを再生成する。SQLマイグレーションがないことと、DBへの更新がないことは別。生成済みHTMLはDBに残るので、コードrevertだけで表示が戻るとは限らない。

自社ページの公開と顧客HTMLの再生成を明示的に分離する。対象限定の試験、既存published_htmlの退避、戻す対象と方法、停止条件を記載し、実際の起動条件と一致させる。バージョン値を戻すだけの運用に依存しない。

### R6 / P2: 設定のpatchはまだ同時更新で古い値を書き戻せる

`app/api/sites/[id]/route.ts:60`〜77。現在の設定をSELECTし、JavaScriptで合成し、別リクエストで全体UPDATEしている。SELECTとUPDATEの間に別画面が通知先やpreviewTokenを変更すると、その変更を古い読取り値で上書きできる。

DBでの原子的な部分更新、または同時変更を検出して再取得・再合成する方式を用いる。同じ設定を書き込む他の経路も含め、旧値の復活を防ぐ。単に順番に保存する試験ではなく、読取りと書込みの間に別更新を挟む試験が必要。

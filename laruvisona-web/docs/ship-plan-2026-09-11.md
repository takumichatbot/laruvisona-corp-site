## 3. 出す順（案）

前提として、**コードのデプロイと、顧客HTMLの作り直しは別の操作**になっている
（`REPUBLISH_ON_BOOT` を立てなければ、デプロイしても顧客サイトは1行も書かれない）。

### 案1: 一度に出して、作り直しだけ段階的にやる（おすすめ）

0. **出す前に、4章を上から読むだけ実行する**（2つのSHA・保存済みHTMLの版の分布・
   `site_domains` の適用状態・設定の有無）。ここで本番へ書く操作は1つも無い
1. 全コミットをまとめて `main` へ入れて push → デプロイ
   - `REPUBLISH_ON_BOOT` は設定しない
   - `DOMAIN_PROBE_SECRET` は、独自ドメインを使うなら先に設定する
2. **Render の Deploys で、新しいSHAが Live になったことを確かめる**
3. 自社の2ページと制作画面を確かめる（顧客サイトの保存済みHTMLはまだ触れていない）
4. 新版の `dryRun` を1回投げ、`dryRun: true` が返ることを確かめる（4-5）
5. `site_domains.sql` を適用する（runbook のとおり）
6. 顧客サイトの作り直しを、1件 → 5件 → 25件 → 全件
   （`docs/rebuild-migration-2026-09-11.md` の段階3。応答は毎回ファイルに保存する）

**利点**: ブランチを分けて持ち続けなくてよい。作り直しを止めれば、顧客サイトの
見え方は保存済みのままにできる。
**注意**: コードは50コミットぶん一気に変わる。自社ページ・管理画面・制作画面は
その場で新しくなる。

### 案2: 独自ドメインだけ後にする

`main` から独自ドメインの12コミットを外したブランチを作って先に出し、
`site_domains.sql` の適用と一緒に後から出す。

**利点**: SQLの適用とコードの反映を完全に揃えられる。
**注意**: 12コミットは他の変更と重なる部分（`proxy.ts`・`lib/public-site-url.ts`）が
あるので、外すと手作業の解消が要る。**コードが壊れないことを確認済みなので、
この手間に見合うかは疑問**（判断は齋藤さん）。

### 4-1. 2つのSHAを、分けて書き留める

```bash
# (a) GitHub main の先端
git ls-remote origin refs/heads/main
```

```
(b) Render が動かしているSHA
    Render の管理画面 → 対象サービス → Deploys
    「Live」になっているデプロイのコミットを控える。
    （Render の実行環境には RENDER_GIT_COMMIT が入るが、
      それを外から読める口はいま無い。画面で確認する）
```

(a) と (b) が違う場合、**本番で動いているコードは (b)** である。
このあとの判断は (b) を基準にする。

### 4-2. 保存済みHTMLの版を数える（読み取りだけ）

Supabase の SQL Editor で実行する。**書き込みは1行も無い。**

```sql
-- 公開中のサイトが、いまどの版のHTMLで保存されているか
select
  coalesce(substring(published_html from '<!--lhpv:([0-9]+)-->'), '（版の印なし）') as version,
  count(*) as sites
from public.sites
where published is true
group by 1
order by 1;
```

「版の印なし」は、印を埋め込む前のコードで公開された行。作り直しの対象になる。

```sql
-- 作り直しの対象になる件数だけを先に知りたいとき（版9に揃っていない行）
select count(*)
from public.sites
where published is true
  and (published_html is null or published_html not like '%<!--lhpv:9-->%');
```

### 4-3. site_domains の適用状態（**表の有無と、移行の完了は別**）

```sql
-- (1) 表があるか。※これは「移行が全部終わった」ことの確認ではない
select to_regclass('public.site_domains') is not null as table_exists,
       to_regclass('public.domain_release_queue') is not null as queue_exists;

-- (2) あとから足した列がそろっているか
select column_name
from information_schema.columns
where table_schema = 'public' and table_name = 'site_domains'
  and column_name in ('operation_epoch','render_register_started_at','external_registration_owned',
                      'release_operation_id','release_lease_until','redirects_to')
order by 1;   -- 6件そろっていれば、列の追加は済んでいる

-- (3) トリガがあるか（sites 側のガードを含む）
select tgname from pg_trigger
where tgrelid in ('public.sites'::regclass, 'public.site_domains'::regclass)
  and not tgisinternal
order by 1;   -- guard_sites_custom_domain_trg / site_domains_touch /
              -- site_domains_enqueue_release_trg

-- (4) 状態遷移の関数がそろっているか
select proname from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname like 'laruhp_domain_%'
order by 1;   -- 8件

-- (5) 権限（authenticated から直接書けないこと）
select grantee, privilege_type from information_schema.role_table_grants
where table_schema = 'public' and table_name = 'site_domains'
order by 1, 2;
```

(1) だけを見て「当たっている」と判断しない。
`site_domains.sql` は表の作成・列の追加・トリガ・関数・権限を1つのファイルで
やっているので、**途中まで当たっている状態**があり得る。(2)〜(5) までそろって
初めて「当たっている」と言える。そろっていなければ、`site_domains.sql` は
`if not exists` / `create or replace` で書いてあるので、**もう一度そのまま流せば
足りない分だけが入る**（`supabase/site_domains_runbook.md`）。

### 4-5. デプロイのあと（新版が動いてから）

ここで初めて、新版の `dryRun` が使える。

```bash
# 新版が動いていること（Deploys が新しいSHAで Live）を確かめてから
curl -X POST -H "Authorization: Bearer $ADMIN_SECRET" -H 'content-type: application/json' \
  -d '{"onlyOutdated":true,"dryRun":true}' \
  https://laruvisona.jp/api/admin/republish-all
```

応答に `dryRun: true` が入っていること、`targets` が返ることを確かめる。
**`dryRun: true` が返らなければ、動いているのは旧版**なので、すぐ手を止める
（旧版は dryRun を無視して作り直しを始めてしまう）。

## 3. 出す順（案）

前提として、**コードのデプロイと、顧客HTMLの作り直しは別の操作**になっている
（`REPUBLISH_ON_BOOT` を立てなければ、デプロイしても顧客サイトは1行も書かれない）。

### 案1: 一度に出して、作り直しだけ段階的にやる（おすすめ）

0. **出す前に、4章を上から読むだけ実行する**（2つのSHA・保存済みHTMLの版の分布・
   `site_domains` の適用状態・設定の有無）。ここで本番へ書く操作は1つも無い
1. 全コミットをまとめて `main` へ入れて push → デプロイ
   - `REPUBLISH_ON_BOOT` は設定しない
   - `DOMAIN_PROBE_SECRET` は、独自ドメインを使うなら先に設定する
2. **Render の Deploys で、新しいSHAが Live になったことを確かめる**
3. 自社の2ページと制作画面を確かめる（顧客サイトの保存済みHTMLはまだ触れていない）
4. 新版の `dryRun` を1回投げ、`dryRun: true` が返ることを確かめる（4-5）
5. `site_domains.sql` を適用する（runbook のとおり）
6. 顧客サイトの作り直しを、1件 → 5件 → 25件 → 全件
   （`docs/rebuild-migration-2026-09-11.md` の段階3。応答は毎回ファイルに保存する）

**利点**: ブランチを分けて持ち続けなくてよい。作り直しを止めれば、顧客サイトの
見え方は保存済みのままにできる。
**注意**: コードは50コミットぶん一気に変わる。自社ページ・管理画面・制作画面は
その場で新しくなる。

### 案2: 独自ドメインだけ後にする

`main` から独自ドメインの12コミットを外したブランチを作って先に出し、
`site_domains.sql` の適用と一緒に後から出す。

**利点**: SQLの適用とコードの反映を完全に揃えられる。
**注意**: 12コミットは他の変更と重なる部分（`proxy.ts`・`lib/public-site-url.ts`）が
あるので、外すと手作業の解消が要る。**コードが壊れないことを確認済みなので、
この手間に見合うかは疑問**（判断は齋藤さん）。

### 4-2. 保存済みHTMLの版を数える（読み取りだけ）

Supabase の SQL Editor で実行する。**書き込みは1行も無い。**

```sql
-- 公開中のサイトが、いまどの版のHTMLで保存されているか
select
  coalesce(substring(published_html from '<!--lhpv:([0-9]+)-->'), '（版の印なし）') as version,
  count(*) as sites
from public.sites
where published is true
group by 1
order by 1;
```

「版の印なし」は、印を埋め込む前のコードで公開された行。作り直しの対象になる。

```sql
-- 作り直しの対象になる件数だけを先に知りたいとき（いまの版に揃っていない行）
-- ※ lib/html-export.ts の EXPORT_VERSION と同じ数字にすること
select count(*)
from public.sites
where published is true
  and (published_html is null or published_html not like '%<!--lhpv:11-->%');
```

### 4-3. site_domains の適用状態（**表の有無と、移行の完了は別**）

Supabase の SQL Editor で、**そのまま1本**流す。`update`/`insert`/`delete`/`grant`/`revoke` は無い。
中身は `supabase/site_domains_state_check.sql` と同じもの（`psql -f` でもよい）。

```sql
-- ── site_domains の適用状態を、読み取りだけで確かめる ────────────────
--
--   psql -f supabase/site_domains_state_check.sql
--   （Supabase の SQL Editor にそのまま貼ってもよい）
--
-- update / insert / delete / grant / revoke は1つも無い。
--
-- 見るのは「宣言が書いてあるか」でも「存在するか」でもなく、

--     （USING(true) も TO service_role も弾く）
--   ・トリガは発火条件（tgtype）と呼出先の関数まで一致するか
--   ・権限は2つの表それぞれについて、列単位・TRUNCATE/REFERENCES/TRIGGER
--     まで含めて見る（表単位の4権限だけでは足りない）
--   ・必要な3ロールが存在するか（欠けていると権限の検査が素通りする）
--   ・列は名前だけでなく型まで、制約は定義文、索引は部分索引でないかまで
--   ・search_path は = で正確に照合（like だと public_shadow が通る）
--
-- 表やロールが無くてもエラーにならない（::regclass ではなく to_regclass）。
-- 未適用なら「対象なし」と出て、判定は false になる。
--
-- 判定は2行ある。
--   98 適用の判定      … site_domains.sql が正しく当たっているか
--   99 望ましい状態    … 98 に「移行SQLの積み残し」を足したもの
-- 区分が「積み残し」の行は、移行SQLを当てただけでは false になる行。
-- **現在この区分の行は無い**（2026-09-11 に site_domains.sql へ
-- `revoke truncate, references, trigger` を足したため）。
-- したがって正しく当たっていれば **98 も 99 も true** になる。
-- 区分そのものは、将来また積み残しが出たときのために残してある。
--
-- **98=true は「独自ドメインを公開してよい」という意味ではない。**
-- 98 は「移行SQLの内容どおりか」だけを見る。公開の可否は 99 で判断し、
-- **99=false のあいだは独自ドメインの有効化を始めない**。
-- 2つの表はどちらも、anon / authenticated に
-- TRUNCATE / REFERENCES / TRIGGER が残っていたら不合格（27/28行・22/23行）。
--

         to_regclass('public.sites')                as sites,
         to_regrole('anon')                         as r_anon,
         to_regrole('authenticated')                as r_auth,

  ('laruhp_domain_mark_register_started(uuid,text,text,bigint)'),
  ('laruhp_domain_mark_release_failed(uuid,text,bigint,text)'),
  ('laruhp_domain_pending_queue(text)'),

  ('laruhp_domain_resolve_queue_entry(uuid,text)'),

need_col(tbl, col, typ) as (values

-- ── 権限は「2つの表 × 2つの利用者ロール」を同じ物差しで見る ──
```

ロールは**データベース単位ではなくクラスタ共有**なので、回帰スクリプトは
ロールの作成をクラスタで1回だけ行い、ロールを変えるケースは必ず元へ戻し、
**ケースごとに開始時の基準状態（98=t / 99=t / 落ちる行なし）を確認**してから
異常を入れる。ケース終了時にロール状態が戻っていなければ、その場で止める。
初期化・異常作成・確認のすべてで `ON_ERROR_STOP` を有効にし、SQLのエラーは握りつぶさない。

そろっていなければ、`supabase/site_domains.sql` を流し直す（適用は出す順の7番）。
ただし**「足りない分だけが入る」わけではない**:

- `create or replace function` は**既存の定義を置き換える**（11本すべて）
- `drop function if exists` で**旧シグネチャを落とす**
- `revoke all` → `grant execute to service_role` で**権限を付け直す**
- `drop policy if exists` → `create policy` で**ポリシーを作り直す**
- `drop trigger if exists` → `create trigger` で**トリガを作り直す**
- 末尾で `sites.custom_domain` が入っている行を `site_domains` へ
  **`insert ... on conflict (host) do nothing` で取り込む**（データが増える）

表・列・索引は `if not exists` なので足されるだけだが、
**関数・権限・ポリシー・トリガは置き換え**で、**データ取り込みもある**。
戻し方は `supabase/site_domains_runbook.md`。

# ショップ・決済の整合性（2026-09-14）

## 修正前に成立した問題

- Stripe Webhookは在庫を減らしてから注文を重複排除していた。同じWebhookの再送で、注文は1件のまま在庫だけが繰り返し減った。
- 同時購入は同じ `settings_json` を読み、後の書き込みが先の在庫減算を上書きできた。
- カートがStripe metadataの500文字を超えると、在庫減算用の明細を黙って省略していた。
- 決済完了時の商品名・金額を現在の商品設定から再構成しており、決済中の編集で購入時点の明細と食い違った。
- 商品の追加・販売停止・削除も読み書きの失敗を確認せず、同時編集で設定を失う可能性があった。

## 実装

- カートは20種類、各99点まで。重複する商品と選択肢をまとめ、450文字ずつ複数のmetadataへ必ず保存する。旧metadataも読み取れる。
- WebhookではStripeの確定済みLine Itemsを取得し、数量と合計金額をカートおよびSession合計と照合する。
- `laruhp_shop_commit_order` がサイト行をロックし、重複Sessionの確認、在庫検査、在庫減算、注文保存を1トランザクションで行う。再送時は既存注文を返し、在庫も通知も増やさない。
- 支払い後に商品が削除・停止されていた場合や在庫不足の場合は、注文を消さず `review`（要確認）で保存する。在庫は部分的に減らさない。
- 注文状態はDBトリガでも一方向に制限した。所有者に許可する列更新は `status` と `note` のみ。
- 商品APIは値と上限を検査し、`updated_at` が読んだ時点と一致する場合だけ保存する。競合時は最大4回読み直し、解消しなければ409を返す。
- 配送先収集の設定も既存の設定patch APIへ通し、他画面の設定を古い値で戻さない。
- ショップと注文管理の絵文字は意味を持つアイコンへ置き換えた。

## 検証

- TypeScriptと対象ESLintは成功。
- カートの上限・分割復元・旧形式、Stripe明細照合、所有境界、同時更新条件、Webhookの処理順を単体回帰にした。
- 行ロックを意図的に外すと回帰が失敗することを確認した。
- `hp_orders_regression.sql` を一時PostgreSQLランナーへ組み込んだ。このMacには `initdb` が無いため、今回の環境ではSQL実行結果を確認していない。本番適用前にPostgreSQL 16で通す。

## 本番適用と残件

本番変更は行っていない。コードより先に更新後の `supabase/hp_orders.sql` を適用する。旧コードは新しい関数を使わないため、先行適用中も既存の購入経路は動く。

実Stripeで、購入成功、Webhook再送、同時購入、在庫不足、通知、注文表示まで確認する。返金処理と返金Webhook同期はまだショップ注文には無いので、画面からキャンセル済みへ変更する操作は提供しない。

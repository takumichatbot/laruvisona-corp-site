# 本格予約の事前リマインド

## 目的

本格予約 `hp_appointments` の確定予約へ、来店24時間前と2時間前にメールを送る。旧固定枠のリマインドとはデータも実行経路も混ぜない。

## 配信の約束

- 予約ID・予約の版・通知種別の組を一意にする。同じ予約日時への同じ通知は、定期実行やHTTP応答が重なっても増えない。
- 日時変更やキャンセル後に残った未送信通知は `obsolete` にする。日時変更後は新しい予約版として通知を作る。
- DBで `FOR UPDATE SKIP LOCKED` を使い、取得票を持つ実行だけが結果を確定する。取得した処理が消えた場合は10分後に回収する。
- Resendへは通知行ID由来の固定idempotency keyを渡す。失敗は最大5回、待ち時間を延ばしながら再試行する。
- 24時間前通知は来店3時間前で締め、2時間前通知と同時に届かないようにする。定期実行が短時間止まっても、締切内なら回復する。
- メール設定が無いときは行を取得せず503を返す。予約の確定自体は通知の成否に依存させない。

## 反映手順

1. `hp_scheduling.sql` が適用済みであることを確認する。
2. `supabase/hp_scheduling_reminders.sql` を1トランザクションで適用する。
3. コードをデプロイする。常時起動プロセスが15分ごとに内部APIを呼ぶため、外部cronの追加は不要。
4. テスト予約を24時間前・2時間前の各範囲に置き、宛先、日時、担当、重複が無いことを確認する。

必要な既存設定は `ADMIN_SECRET` と `RESEND_API_KEY`。値はログや文書に残さない。

## 戻し方

まず定期呼び出しを含むコードを戻す。表は送信監査記録なので残す。未送信行がある状態で表を削除しない。

ローカルではTypeScript回帰を実行済み。使い捨てPostgreSQLの検査は `tests/scheduling/run.py` に統合しているが、PostgreSQL実行ファイルがある環境で別途実行する。

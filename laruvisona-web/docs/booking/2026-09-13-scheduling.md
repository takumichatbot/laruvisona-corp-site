# 担当者・設備の本格予約

## 今回の実装

- 営業時間（曜日ごと・最大4区間、昼休み）、休業日、担当者の勤務時間と休日。
- メニューの所要時間・後片付け時間・来店時料金・対応可能な担当者・設備候補。
- 空いている担当者1人と、設備候補のうち空いている1つを確保する。設備候補を選ばなければ設備は不要。同時に複数種類の設備を1予約へ割り当てる方式ではない。
- お客様がメニュー・担当者（指名なしも可）・空き日時を選び、予約を即時確定する。
- お客様は確認リンクから期限内に日時変更・キャンセル。店舗は予約一覧から日時変更・キャンセル。
- 新規・変更・キャンセルをイベントとして保存。メールは確定処理の後に送信し、失敗しても予約を消さない。店舗に未確認の通知と再送操作を表示する。
- 初期状態は受付停止。管理画面で設定を保存して有効化する。
- 日本時間固定。端末が別のタイムゾーンでも日付・時間を変えない。

入口: `/laruHP/booking/schedule`。公開予約: `/hp/<slug>/reserve`（顧客の独自ドメインは `/reserve`）。
ビルダーの予約モード「担当者・設備の本格予約」で、サイトに空き枠ページへのボタンを追加できる。以前の固定枠・リクエスト画面も残す。
EXPORT_VERSION: 14→15。既存顧客HTMLの一括再生成は不要。利用者が新しい予約モードを選んで公開したときに反映する。

## 二重予約・確認できない状態の扱い

空き枠の表示だけでは確保しない。確定直前にサイトの行をロックし、同じ計算で空きを再確認して予約と担当者・設備の割当を1トランザクションで保存する。さらに `tstzrange` の排他制約で同じ担当者・設備の時間の重複をDBが拒否する。範囲は開始を含み、準備終了を含まない `[)`。

日時変更は新しい枠を確認してから割当を置き換える。失敗はトランザクション全体を取り消すので、元の予約が残る。設定・予約とも版を照合し、古い画面からの上書きを409で拒否する。表示後に価格やメニュー設定が変わったときも、再確認するまで新規予約を確定しない。

予約ごとの256bit確認キーはブラウザで生成する。DBにはハッシュのみ保存。キーは確認URLのフラグメントとAPIのAuthorization/bodyで扱い、URLクエリに載せない。予約確認ページはnoindex・no-referrer。会社のGoogle Analyticsとチャット埋め込みをこのページでは読み込まない。確認URLを持つ人は予約を変更できるため、共有しない旨を画面に表示する。

送信前に同じ送信ID・確認キー・入力をsessionStorageへ控える。応答が消失したら入力を固定し、同じIDで再確認する。再読み込みでも予約結果を先に回収し、別予約を作らない。ブラウザの保存機能が使えない場合は予約送信前に止める。確定後に控えを消す。

メールには予約番号・確定日時を載せる。確認キーはメールイベントに保存せず、確認リンクは完了画面でコピーする。リンクを失った場合は店舗に連絡する。メール送信は各宛先別の記録とResendの冪等キーを使う。受付から23時間を過ぎた未確認送信は自動再送しない（プロバイダーの冪等期限を超えた二重送信を避ける）。通知済みはメールサービスへの受付成功であり、受信箱への到達確認ではない。

## 旧固定枠からの切り替え

- 旧 `hp_reservations` に未完了の決済待ち、または未来の確定予約があれば有効化を拒否する。
- 有効化と旧予約INSERTは同じサイトの行ロックで直列化する。切り替え後に旧APIから予約が割り込むことはDBトリガが拒否する。新方式の受付を停止しても、未来の新予約が残っているあいだは旧予約を入れられない。
- 旧固定枠の空きAPIは、新方式が有効なら新しい入口を返す。新しく公開したカレンダーブロックもそのリンクを表示する。保存済みの旧HTMLがその表示処理を持たない場合、店舗は予約ブロックのモードを切り替えて再公開する。
- 旧テーブルが存在しない環境にも適用可能。ただし、後日旧テーブルを追加する場合は、この移行SQLを再適用してトリガも設置する。
- 新方式のSQLが未適用なら、旧固定枠APIは従来のまま。DB接続障害を「新方式なし」と誤認して処理を続けない。

## 導入と戻し方

今回の作業では本番DB・本番デプロイ・実送信は行わない。

1. 対象のコード差分と `supabase/hp_scheduling.sql` をレビューする。
2. 本番の `hp_reservations` と、新設4表・5関数の有無を読む。別実装が同名で存在する場合は停止して照合する。
3. 承認された環境で `supabase/hp_scheduling.sql` をトランザクションとして適用する。`btree_gist` 拡張、4表、5関数、旧予約を保護するトリガを追加する。既存予約の書き換え・削除は行わない。
4. 新コードをデプロイ。起動時の顧客HTML再生成は行わない。
5. テスト店舗で設定→受付開始→予約→変更→キャンセルを確認。既存予約がある店を勝手に切り替えない。
6. 実Supabase Authで他店舗を読めないこと、RESEND_API_KEYと店舗の通知先が正しいこと、実メール受信を確認する。

異常時は店舗の受付を停止する。既存予約はそのまま参照・キャンセルできる。予約がある状態でコードだけ旧版へ戻すと、新予約の管理画面がなくなるため、先に予約と通知状況を保全し運用方法を決める。4表や割当行を自動で削除しない。旧固定枠へ戻す場合も将来の新予約と二重予約しないよう運用確認が必要。

## 検証と範囲

- 単体: 設定検証、営業時間の重複、壊れた日付、担当者・設備の参照、匿名入力、HTMLへの実リンク、旧APIのDB障害。
- `python3 tests/scheduling/run.py`: 完全に新しいローカルPostgreSQLクラスタでSQLを適用し、RLS・権限・時間の衝突・キャンセル・版の競合・12接続同時予約などを確認する。共有DBは使わない。
- `tests/scheduling/browser.mjs`: Nextの本番用ビルドを実ブラウザで操作。認証だけは固定セッションを使い、予約・設定・割当・キャンセルはHTTP経由で実PostgreSQLへ書く。応答を1回だけ遮断する対照を含む。
- 320/390/1440pxで設定画面、390pxで予約→変更→店舗側確認を検証。米国タイムゾーンでも日本時間の10時が表示されることを確認。
- 実Supabase Auth、実メール受信、実店舗データ、実機Safariは別途本番前に確認する。テスト中のメール送信は無効。
- 料金は来店時払い。承認制・オンライン事前決済・メール確認による予約成立・LINE/SMS・複数設備同時確保は今回の新方式に含めない。従来の固定枠の事前決済は別方式として維持する。

# 問い合わせ受付と顧客対応の信頼性

## 見つかった問題

- 問い合わせ管理APIは、DBの読み取り・更新・削除が失敗しても成功を返していた。
- 一括更新は問い合わせIDをクエリに付けていたが、APIは本文だけを読んでいたため、実際には更新していなかった。
- 管理画面はAPIの結果を確認せず、保存・削除・一括更新を成功表示していた。
- 管理画面が使うCRM列と所有者の削除ポリシーが、再現可能なSQLに含まれていなかった。
- 公開フォームの入力が通知メールのHTMLへそのまま入っていた。
- Content-Lengthを持たない大きな本文を制限する仕組みがなかった。

## 変更

- 公開フォームの入力契約を `lib/contact-contract.ts` に集約した。サイトID、種別、氏名、メール、電話、本文、追加項目の型・件数・長さを制限する。
- リクエスト本文はストリームで100KBまで読み、上限を超えた時点で中止する。
- 通知メールへ入るサイト名・氏名・本文・追加項目をHTMLエスケープし、メール件名から改行を除く。
- 問い合わせの保存に失敗した場合は503を返す。通知先が未設定でも、保存済みの受付を失敗扱いにして再送を促さない。
- 管理APIはDBエラーを503、所有していない・存在しない対象を404にする。更新・削除は返された行が1件のときだけ成功とする。
- 管理画面は成功した対象だけを更新し、失敗した入力や選択を残す。
- 管理画面の絵文字を製品のアイコン体系へ置き換えた。
- `supabase/contacts_crm.sql` にCRM列、制約、所有者の更新・削除ポリシー、必要権限を定義した。既存行を保持したまま再適用できる。
- `supabase/contacts_crm_regression.sql` に、所有者だけが閲覧・更新・削除でき、他テナントの行を変更しない回帰を追加した。

## 本番反映時の注意

アプリのデプロイ前に `supabase/contacts_crm.sql` を適用し、SQL回帰または本番読み取り確認で列とポリシーを確認する。今回、本番DBへの接続・SQL適用は行っていない。

# 注文管理の信頼性（2026-09-14）

## 直した問題

- 注文状態を画面で先に変更していたため、DB更新が失敗しても成功したように見えていた。
- 更新対象にサイト所有者の条件を明示せず、更新0件も成功扱いだった。
- 「キャンセル」はStripe返金を実行しないのに選択でき、返金済みと誤認させる状態だった。
- 注文一覧がブラウザから直接DBを読み書きし、DBのエラー文をそのまま表示していた。

## 変更

- 認証済みの `/api/orders` に一覧と状態変更を集約した。
- 所有サイト、UUID、許可した状態遷移を検証し、更新は直前状態を条件にした。競合・更新0件・DB失敗を成功にしない。
- 状態は `入金済 → 発送済 → 完了` の一方向とし、入金済から完了への直接変更も許可する。既存のキャンセル注文は表示するが、返金機能が無い画面から新しくキャンセルへ変更できない。
- UIはAPI成功後にだけ表示を更新する。失敗時は元の状態と入力を保つ。
- 絵文字を製品UIから外し、意味を持つアイコンと文字へ置き換えた。
- `hp_orders` は所有者のSELECT/UPDATEだけを許可し、匿名・ログイン利用者のINSERT/DELETEを明示的に閉じた。

## 未完了として分けるもの

Stripe返金、返金状態のWebhook同期、在庫更新のトランザクション化は別の変更単位で扱う。返金を確認する前にキャンセル済みと表示しない。

## 本番適用

本番変更は行っていない。コードを出す前に `supabase/hp_orders.sql` を適用し、所有者の一覧・状態変更、他テナントの非表示、匿名の書き込み拒否を確認する。
